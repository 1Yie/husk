# Native File-Tool Spec — `smart_read` + `fuzzy_patch`

Design goal: **file IO is where the Rust stack beats script-harness agents decisively.** No `cat`, no full-file rewrites, no line-number diffs. Structured reads and search-and-replace blocks cut token spend ~85% and apply edits in sub-millisecond time, in-process.

## Why the naive primitives fail

| Naive approach | Failure |
|----------------|---------|
| `cat file` | 2000-line dump for one function — ~10k tokens, plus "lost in the middle" attention dilution |
| Full-file rewrite | model re-emits every line at token-rate speed; high truncation/`// rest unchanged` corruption risk |
| Standard unified diff | `@@ -12,6 +12,7 @@` hunks break on hallucinated line numbers → `Hunk FAILED` → retry storm |

## `smart_read` (`agent-kernel/src/tools/fs_read.rs`)

Three modes — the model picks the cheapest that answers its question:

| Mode | Args | Output | Cost |
|------|------|--------|------|
| `outline` | `path` | tree-sitter skeleton: signatures, types, doc comments; bodies folded to `{ … }` | ~100 tok for a 2k-line file |
| `range` | `path`, `start`, `end` | numbered lines `NNNN │ code`, hard cap `max_lines` | ~100–300 tok |
| `search` | `path`, `pattern` | match lines + line numbers (or use `grep` tool for cross-file) | small |

Contract details:

- **Line numbers are always emitted** in `range` mode (`{:>4} | {}`) so a follow-up patch can anchor without a second read.
- Every response carries `content_hash` (cheap `xxh3`/`blake3` of the read window) — `fuzzy_patch` can optionally require it to detect file drift between read and write ("file changed since you read it").
- `outline` uses `tree-sitter` per-language; unsupported languages degrade to a `range` head-read + a notice, never an error.
- Same truncation discipline as everything else: `range` hard-caps at `max_lines` (default 1000) with a `… [truncated] …` marker.

## `fuzzy_patch` (`agent-kernel/src/tools/fs_patch.rs`)

Model emits a **search/replace block**, never a diff:

```json
{ "path": "src/engine.rs",
  "search": "fn run_loop(&mut self) {\n    self.state = State::Idle;\n}",
  "replace": "fn run_loop(&mut self) {\n    self.state = State::Running;\n    self.notify();\n}",
  "expected_hash": "optional — content_hash from smart_read" }
```

Match pipeline (ordered, first success wins):

1. **Normalize**: `\r\n` → `\n` on source + both blocks (cross-platform line endings are the #1 silent failure).
2. **Exact match**: `match_indices` on normalized source.
   - 0 hits → tier 3.
   - 1 hit → apply.
   - >1 hits → `Err("matched N locations — add surrounding context lines")`: the error message itself instructs the model how to fix the call. This is deliberate — ambiguous auto-picks are how agents corrupt files.
3. **Whitespace-tolerant**: normalize leading/trailing whitespace per line, retry match.
4. **Fuzzy (last resort)**: sliding-window Levenshtein (`similar::get_close_matches` or strsim) with similarity ≥ 0.9; a fuzzy-applied patch is **flagged** in the result so the approval card can say "matched approximately (92%) — review carefully".
5. **Hash check**: if `expected_hash` provided and the file's current hash differs → `Err("file drifted — re-read")` before any match attempt.

Return value:

```rust
pub struct PatchResult {
    pub patched_content: String,   // written to CoW snapshot / real file after approval
    pub unified_diff: String,      // generated by `similar` — feeds DiffViewer
    pub matched_fuzzily: bool,
    pub match_line: usize,
}
```

`apply_patch` (multi-hunk unified diff) still exists for genuinely multi-site changes, but `fuzzy_patch` is the default edit tool — it covers ~90% of edits with a far simpler model contract.

## The edit loop end-to-end

```text
smart_read(outline) → locate symbol
smart_read(range 135..190) → exact lines + content_hash
fuzzy_patch(search, replace, expected_hash)
    → PatchResult.unified_diff
    → CoW snapshot apply (if snapshot on)
    → UiEvent::AwaitingApproval(diff) → Slint DiffViewer
    → approve → write + RecordAgentWrite(hunks, origin:agent)
    → verify: cargo check / targeted test → observe → done
```

## Token economics

| | naive (`cat` + rewrite) | native (`smart_read` + `fuzzy_patch`) |
|---|---|---|
| Tokens/turn | 3,000–10,000+ | 200–500 (**~85% less**) |
| Wall time | 5–15 s (token-rate bound) | <1 s (few patch lines to generate) |
| Failure modes | truncation, lazy `// unchanged`, hunk line drift | unique-match ambiguity → clear retry instruction |

## Non-negotiables

- In-process only — no `cat`/`patch`/`sed` subprocess for file IO (the `bash` tool remains for builds/tests).
- Ambiguity errors must **teach the fix** ("add context lines"), not just fail.
- Fuzzy matches are never silent — flagged in the result and on the approval card.
- `content_hash` drift aborts before matching — stale-context writes are a top corruption source.
- All path checks canonicalize before prefix compare (symlink escape — see sandbox-model).

## Acceptance checklist

- [ ] `smart_read` outline of a 2k-line file returns ≤150 lines of skeleton
- [ ] `fuzzy_patch` on CRLF file with LF search block applies cleanly
- [ ] Duplicate `search` block → error names the match count and demands context
- [ ] Stale `expected_hash` → refused before matching
- [ ] Patch → approval card shows unified diff + fuzziness flag when applicable
